Hosting on your own domain

Two separate things can be published, and they have different requirements. Getting this distinction right is most of the work.

WhatWhere it can liveWhy
These docs (static HTML) GitHub Pages, behind Cloudflare or a GoDaddy CNAME Public, static, no data. A CDN is exactly right.
The app (uploads, index, model) A machine you control, published via Cloudflare Tunnel or a VPS It holds your documents and runs the model. GitHub Pages cannot host it — Pages serves static files only, and putting documents on a CDN would defeat the entire point.
Do not commit data/. It holds uploaded documents, the index, and the catalog. It is gitignored — keep it that way. Publishing your documents to a public repository is the exact outcome this project exists to prevent.

Part 1 — Publish the docs on GitHub Pages

The workflow at .github/workflows/pages.yml deploys the docs/ directory on every push to main. Enable it once:

  1. Repository → Settings → Pages.
  2. Source → GitHub Actions.
  3. Push to main. The site appears at https://<user>.github.io/JJRAG/.

Point your own domain at it — Cloudflare

If your domain's nameservers are at Cloudflare:

  1. Cloudflare dashboard → your domain → DNS → Records.
  2. Add a CNAME: name docs, target <user>.github.io, proxy status DNS only (grey cloud) for the initial certificate issuance. You may turn the orange cloud back on once GitHub reports the certificate as issued.
  3. Back in GitHub → Settings → Pages → Custom domain, enter docs.example.com and save. This writes a CNAME file into the published site.
  4. Tick Enforce HTTPS once the certificate is issued (usually minutes; occasionally up to an hour).

Point your own domain at it — GoDaddy

If your domain stays on GoDaddy's nameservers:

  1. GoDaddy → My Products → Domain → DNS → Manage Zones.
  2. Add a CNAME: Name docs, Value <user>.github.io, TTL 1 hour.
  3. For the apex domain (example.com with no subdomain), GoDaddy does not support CNAME at the root — add four A records instead, pointing at GitHub's Pages addresses: 185.199.108.153, 185.199.109.153, 185.199.110.153, 185.199.111.153.
  4. Set the same custom domain in GitHub → Settings → Pages, then enable Enforce HTTPS.

Verify propagation before assuming something is broken:

dig +short docs.example.com CNAME
curl -sI https://docs.example.com | head -n 1

Part 2 — Publish the app

Option A — Cloudflare Tunnel (recommended)

This is the best fit for a local-model system. Your machine keeps the documents and the model, opens only an outbound connection to Cloudflare, and serves a public hostname over HTTPS. No inbound firewall rule, no public IP, no port forwarding — so this works from an office box or a home server that has no business being directly reachable.

  1. Cloudflare Zero Trust dashboard → Networks → Tunnels → Create a tunnel → name it jjrag → copy the token.
  2. Put the token and an API token in deploy/.env (copy deploy/.env.example): 
    JJRAG_API_TOKEN=$(openssl rand -hex 32)
CLOUDFLARE_TUNNEL_TOKEN=eyJhIjoi...
  3. Start the stack with the tunnel profile: 
    docker compose -f deploy/docker-compose.yml --profile tunnel up -d
docker compose -f deploy/docker-compose.yml exec ollama ollama pull llama3.1:8b
  4. In the tunnel's Public Hostname tab, route app.example.com → http://app:8000.

Then put Cloudflare Access in front of it (Zero Trust → Access → Applications). That gives you SSO, per-user policies and a login audit trail without writing any auth code — and it means the app is not exposed to the open internet even though it has a public hostname.

Option B — Your own VPS

Use this when the domain's A record points at a server you control — a GoDaddy-registered domain aimed at a VPS, for instance. The app binds to loopback and nginx terminates TLS in front of it.

  1. DNS: an A record for app → your server's IP (at Cloudflare or GoDaddy, whichever holds the zone).
  2. Deploy the stack, then install the reverse proxy config: 
    sudo cp deploy/nginx.conf /etc/nginx/sites-available/jjrag
sudo ln -s /etc/nginx/sites-available/jjrag /etc/nginx/sites-enabled/
sudo certbot --nginx -d app.example.com
sudo nginx -t && sudo systemctl reload nginx
  3. Confirm the app itself is not reachable except through nginx: ss -tlnp | grep 8000 should show 127.0.0.1:8000.

deploy/nginx.conf already sets the two things people usually get wrong: proxy_buffering off on /api/query/stream (or streamed answers arrive all at once at the end) and a client_max_body_size matching your upload cap.

Option C — Bare metal, no Docker

sudo cp deploy/jjrag.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now jjrag

Before you expose it publicly

  • Set an API token. security.api_token, or JJRAG_API_TOKEN. Without it, uploads and deletions are unauthenticated. jjrag doctor fails when environment: prod and no token is set.
  • Decide about anonymous reads. allow_anonymous_read: false requires the token for querying too.
  • Put an identity layer in front — Cloudflare Access, or your own SSO proxy. The bearer token is a shared secret, not user management.
  • Keep trusted_proxy_header honest. It is set to cf-connecting-ip for Cloudflare. Behind plain nginx use x-real-ip; with no proxy at all, set it to null, or clients can forge it and defeat rate limiting.
  • Back up data/. The catalog and index are rebuildable from the originals; the originals are not rebuildable from anything.
  • Set a retention policy if your obligations require one: security.retention_days.
