Pipeline reference

Eight stages, each with typed inputs and outputs, each gated. A run either publishes a validated index or fails with a named rule and changes nothing.

scanextracttransformassemble embedloadpublish

1 · Scan — admission control

Uploads are untrusted input. Before a file is opened by a parser it must pass: an extension allowlist, a magic-byte check that the content matches the extension, a size cap, a zip-bomb expansion-ratio check for OOXML containers, and a macro-payload check. Rejected files move to data/quarantine/ with a .reason.txt beside them — never silently dropped, because an auditor needs to see what was refused.

Files whose SHA-256 is already in the catalog are skipped, which makes re-running ingestion on a directory idempotent and cheap.

2 · Extract — bytes to text, with provenance

One extractor per format, all producing the same record shape. Extraction is segment-aware: a PDF page, a slide, a CSV row-group and an email body each become a segment with a human-readable label. That label is what a citation shows the reader — report.pdf, p. 12 — and it is the difference between an answer you can check and one you have to trust.

A parser failure on one file never aborts the run; it is recorded and surfaced by the validation stage.

3 · Transform — clean, redact, chunk

Most retrieval quality is won or lost here, in this order:

  1. Normalise — Unicode NFKC, ligatures, smart quotes, control characters, whitespace. Two spellings of one word must not become two vectors.
  2. De-hyphenate — PDFs break words across lines (compli-\nance); rejoining them is the single highest-value cleanup for PDF corpora.
  3. Strip boilerplate — lines repeating on most pages are headers and footers, and they otherwise crowd real content out of the top-k.
  4. Redact PII — before anything is persisted, with typed placeholders that keep sentences readable and co-reference intact.
  5. Chunk — recursively on natural boundaries (paragraph, then sentence, then word), with overlap so an answer spanning a boundary stays retrievable.
  6. Deduplicate — exact by hash, near-duplicate by token shingle overlap, across the whole corpus.
The original prototype used a 1,000-character chunk with 150 of overlap; those remain the defaults. Chunks can exceed chunk_size by up to chunk_overlap, which the max_chunk_chars gate accounts for.

4 · Validate — the gates

A RAG system fails quietly: nobody sees a broken pipeline, they just get worse answers. Validation runs at every stage boundary and makes failure loud. Any error-severity finding fails the run by default (validation.max_error_issues: 0).

5 · Assemble — why every run is a full rebuild

Each run re-indexes every active document, not only the new files. That is what keeps deletions, retention sweeps and configuration changes actually reflected in what gets searched, and it makes index/catalog drift structurally impossible. Because embeddings are cached by (model, text hash), the repeated work costs almost nothing — a re-run of an unchanged corpus is a 100% cache hit.

6 · Embed — local backends

BackendUse when
sentence-transformersDefault. Weights downloaded once at install, then fully offline.
ollamaYou want one model runtime for both embedding and generation.
hashingCI, smoke tests, or air-gapped hosts that cannot fetch weights at all. Deterministic and dependency-free; keyword retrieval still works.

7 · Load and publish — atomic versions

A run writes data/index/v7/ beside the live v6/ and only rewrites the current pointer once every gate has passed — and the pointer write is an atomic rename. So a failed run leaves the previous index serving traffic untouched, and rollback is a pointer move: 

# roll back to the previous published version
python -c "from jjrag.config import get_settings; \
from jjrag.store.vectorstore import VectorStore; \
s=get_settings(); \
print(VectorStore(s.paths.index_dir).rollback())"

Retrieval

Dense-only search misses exact terms — an invoice number, a policy code like DR-14, a surname. Keyword-only search misses paraphrase. JJRAG runs both and fuses them with Reciprocal Rank Fusion, which needs no score calibration between two very different scales. MMR then trims the candidates to top_k, trading a little relevance for diversity so the context window is not three near-identical paragraphs from one page.

Operating it

jjrag doctor                     # environment check
jjrag ingest ~/docs              # run the pipeline
jjrag ingest --force ~/docs      # re-ingest already-indexed files
jjrag rebuild                    # re-index after a config change
jjrag runs                       # run history
jjrag runs run_abc123            # full validation report as JSON
jjrag docs                       # indexed documents
jjrag rm doc_abc123              # erase a document and rebuild
jjrag query "..." --retrieve-only  # inspect retrieval without generating
jjrag serve                      # web app

Everything above is also available over HTTP — /api/ingest, /api/runs/{id}, /api/documents, /api/query — with the interactive schema at /api/docs.
