Compliance controls

Each control below states what it does and — more usefully — how to check it yourself. A control you cannot verify is a claim, not a control.

1 · No third-party model API exists in the code

Not disabled behind a flag, not an optional import: absent. There is no anthropic, openai or other hosted-model client in the dependencies or the source, and CI fails any pull request that adds one. 

# nothing to find
grep -rE "^\s*(import|from)\s+(anthropic|openai|cohere|mistralai)\b" jjrag/
grep -riE "^(anthropic|openai|cohere|mistralai)" requirements.txt pyproject.toml

2 · Outbound connections are blocked at the socket layer

With security.enforce_local_only: true (the default), the process patches the socket layer at startup so any connection outside loopback and the configured model host raises EgressBlocked before a byte leaves. A dependency that tries to phone home fails loudly instead of succeeding quietly. 

python -c "
from jjrag.security import egress
import socket
egress.install(['http://localhost:11434'])
try:
    socket.getaddrinfo('api.openai.com', 443)
    print('NOT BLOCKED')
except egress.EgressBlocked:
    print('blocked as expected')
"

Every blocked attempt is recorded and served at /api/compliance, so an operator can see whether anything tried.

In Docker the same guarantee is enforced a second way, at the network layer: the app and the model sit on a Docker network declared internal: true, which has no route off the host at all.

3 · PII is redacted before storage

Emails, phone numbers, national ID numbers, payment cards (Luhn-checked), IBANs (mod-97 checked), IP addresses and API keys are replaced with typed placeholders during transform — before any text reaches the index — and the result is re-scanned afterwards. Residual PII fails the run by default. 

curl -s localhost:8000/api/compliance | python -m json.tool
# → pii_redaction_enabled, pii_types_redacted

Logs get the same treatment independently: a filter scrubs PII out of every record on its way to a handler, so a stray debug line cannot leak what redaction removed.

4 · Every run is auditable

Each run writes a manifest recording:

  • which files were admitted, and which were rejected and why;
  • how many chunks each document produced;
  • what was redacted, by type and count;
  • every validation finding, by rule and severity;
  • the index version published;
  • a fingerprint of the settings that affect index contents, so two runs that differ can be explained.
jjrag runs                    # history
jjrag runs run_abc123         # full manifest as JSON
sqlite3 data/catalog.sqlite3 "SELECT rule, severity, message FROM validation_issues"

Separately, an append-only audit log at data/logs/audit.jsonl records privileged actions — uploads, rejections, ingests, deletions, queries, rejected authentications — with actor and outcome.

5 · Erasure reaches the vectors

Deleting a document marks it in the catalog and rebuilds the index without it. A "deleted" document that remains retrievable is not deleted; here the vectors go too. 

jjrag rm doc_abc123
# or: curl -X DELETE -H "Authorization: Bearer $TOKEN" \
#          localhost:8000/api/documents/doc_abc123

Set security.retention_days to erase automatically past a deadline.

6 · Uploads are treated as hostile

ControlRejects
Extension allowlistAnything not explicitly permitted.

Expansion-ratio checkZip bombs inside OOXML containers.

Rejected files are quarantined with their reason, not deleted, so refusals stay reviewable.

7 · The browser is locked down

The app serves a strict Content-Security-Policy (default-src 'self', no third-party origins at all), X-Frame-Options: DENY, nosniff, Referrer-Policy: no-referrer, and HSTS in production. The UI ships no external fonts, scripts or analytics — there is nothing to leak a document title to. 

curl -sI localhost:8000/api/health | grep -i content-security-policy

Live attestation

GET /api/compliance returns the running instance's actual posture — not what a document claims, but what the process is configured to do right now. It is unauthenticated by design so a reviewer can check it without credentials, and it exposes configuration only, never content. 

{
  "posture": {
    "generation_provider": "ollama",
    "generation_model": "llama3.1:8b",
    "third_party_model_apis_enabled": false,
    "egress_restricted_to_localhost": true,
    "pii_redaction_enabled": true,
    "validation_gates_enabled": true,
    "audit_log_enabled": true
  },
  "egress_guard_active": true,
  "blocked_egress_attempts": []
}

What this does not do

Being straight about the boundaries is part of the control set:

  • It is not a substitute for your own review. These are engineering controls; whether they satisfy a specific regulation is a determination only you and your counsel can make.
  • Encryption at rest is the host's job. Use full-disk or volume encryption; JJRAG stores files and SQLite databases in plain form on whatever filesystem you give it.
  • The bearer token is not user management. It is one shared secret. Put an identity provider in front for real multi-user access.
  • PII detection is pattern-based. It is deliberately strict about structure (Luhn, mod-97) to limit false positives, which means an unusual identifier format may pass. Review the redaction counts on your own corpus rather than assuming complete coverage.
  • Local models still make mistakes. Grounding and citations make errors checkable; they do not make them impossible.
